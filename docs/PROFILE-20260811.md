# WANOPT latency profile — 2026-08-11

This profile explains the current high latency and low single-flow throughput
of the experimental WANOPT path. It is a diagnostic report, not a release
claim. The live `wanoptd-dev.service` on `:12443` was not changed. All WANOPT
listeners used isolated ports (`:12450`, `:12451`, and `:12452`) and the
instrumented build from commit `b9535d9` (asynchronous cumulative ACKs).

## Method

The client ran on the China-side workstation and was bound with
`--local-address auto`, which selected the physical IPv4 address rather than
the Clash TUN. The fixed egress was `23.135.236.244` with SNI
`icourses-dev.01.me`. The US-side HTTP oracle was a temporary bounded
`python3 -m http.server` on `:28082`, serving exact 1-KiB, 1-MiB, and 10-MiB
zero-filled objects. TUIC was the existing local SOCKS endpoint on
`127.0.0.1:12086`; it and the production listener were left untouched.

Measurements combined:

- interleaved serial 1-KiB requests through TUIC, pooled WANOPT `bbr-tuic`,
  and pooled WANOPT BBR-shaped (`--congestion bbr`);
- fresh independent WANOPT 1-KiB requests;
- exact 1-MiB single-flow downloads;
- a four-lane logical WANOPT flow;
- one-second US-side Prometheus scrapes during an active download;
- server `pidstat` and a client macOS `sample` CPU profile; and
- direct ICMP loss/RTT measurements to the fixed egress.

A curl row was considered complete only for HTTP 200, curl exit 0, and the
expected byte count. Partial rows remain useful for diagnosing stalls.

## Results

### Path health

The direct path itself was impaired during the campaign:

```text
20 ICMP probes to 23.135.236.244
13 replies (35% loss)
RTT min/mean/max/stddev = 192.9 / 208.1 / 288.2 / 23.7 ms
```

ICMP loss is not a complete characterization of UDP loss, but it establishes
that the China-to-US path was not a clean 200-ms link. A direct HTTP request
to the temporary oracle also failed to complete an exact 1-MiB body during
the same window, so the impairment was not created solely by the WANOPT
framing layer.

### Warm short requests

Ten interleaved 1-KiB requests per profile used persistent connections. Every
row returned HTTP 200 and exactly 1,024 bytes. The values below are total curl
times in seconds (median and maximum of the ten observations):

| Profile | Median | Maximum |
|---|---:|---:|
| TUIC (existing persistent endpoint) | 0.248 | 0.472 |
| WANOPT pooled `bbr-tuic` | 0.594 | 1.205 |
| WANOPT pooled BBR-shaped | 0.441 | 1.502 |

The asynchronous ACK change removes the previous receiver-side possibility
of blocking application delivery on every protocol ACK, but it cannot remove
loss and retransmission delay in the shared QUIC connection. The US server's
per-flow instrumentation during the same rows reported authentication in
roughly 0.01–0.35 ms, `OPEN_FAST` processing at 0 ms, and destination TCP
dials of roughly 0.35–0.66 ms. Thus the remaining sub-second-to-second tail is
on the China↔US transport and flow close, not DNS, TLS certificate work, or
the US destination.

There is also a smaller intentional WANOPT close-path floor. Many healthy
short-flow traces cluster very close to 0.500 s. The receiver currently keeps
the lane alive for `remoteFinDrainGrace = 500 ms` after an expected destination
reset so a final ACK can cross a roughly 200-ms path before cleanup
([mpflow.go](../internal/pep/mpflow.go#L44),
[mpflow.go](../internal/pep/mpflow.go#L515)). This is not the explanation for
the multi-second cold tails, but it can contribute materially to a warm
one-shot request. Reducing it is a possible optimization only after a
loss-injection campaign proves that tombstone replay still covers the close
race.

### Cold independent requests

Five fresh independent WANOPT `bbr-tuic` 1-KiB flows took:

```text
1.387, 5.391, 5.853, 3.799, 2.727 s
```

The median was 3.799 s and the maximum 5.853 s. Client debug logs showed
QUIC dial durations from hundreds of milliseconds to about 1.5 s, followed by
additional handshake/stream-open delays. This is the cost that pooling
amortizes; it is not attributable to the remote destination. A cold WANOPT
flow still has a QUIC handshake, authentication/control frames, and a new
destination connection. The path's loss causes PTO/retransmission gaps in
the first exchange.

### Active bulk telemetry

During an exact 1-MiB download through one pooled `bbr-tuic` lane:

```text
curl: HTTP 200, exact 1,048,576 bytes, 30.57 s, 34.3 KiB/s
smoothed RTT: approximately 0.19–0.22 s
controller mode: ProbeBW, recovery: 1
controller max delivery estimate: approximately 23–58 KiB/s
pacing rate: approximately 64 KiB/s (the configured safety floor)
congestion window: approximately 14–30 KiB
controller-reported loss: approximately 1.4–1.9 MiB / 1,200–1,600 packets
```

The sender transmitted roughly 5 MiB over QUIC to deliver 1 MiB of
application data. The low controller estimate and small congestion window
therefore directly explain the ~34-KiB/s goodput and the long completion
time. The built-in QUIC connection loss counters are not authoritative when a
custom controller is installed; the controller loss telemetry is the useful
directional signal here.

As a controller separation check, an otherwise identical WANOPT BBR-shaped
(`--congestion bbr`) server and client completed one exact 1-MiB flow in 6.39 s
(164 KiB/s). During that flow BBR-shaped reported a delivery estimate around
24.8 MiB/s and a window around 399 KiB, while also observing loss and recovery.
This is not evidence that the BBR-shaped controller is production-safe: it is
evidence that the current TUIC-aligned controller is much more conservative
under this loss pattern.

With four WANOPT `bbr-tuic` lanes carrying one logical flow, the server
completed an exact 1-MiB body in about 6.6 s. Lane bytes were approximately
458,957 + 196,608 + 196,608 + 196,608. Multiple lanes helped by providing
independent loss/recovery state, but they also required several independent
QUIC handshakes and produced lane-close churn in other attempts. This is a
valid multipath result, not proof that a fixed four-lane topology is suitable
for interactive traffic.

### CPU and memory

During the 30–31 s 1-MiB transfer, the US process used about 3–7% CPU
(5.2% average in `pidstat`) and approximately 14 MiB RSS. The client macOS
sample was dominated by Go runtime waits, socket reads, and QUIC event-loop
sleep; it did not show a CPU-bound WANOPT stack. Authentication and destination
dial work were sub-millisecond after the transport was established.

## Causal conclusion

The high latency has three separable components:

1. **The path is currently lossy and variable.** The measured 35% ICMP loss
   and 208-ms mean RTT create QUIC PTOs and delayed tails. No proxy framing
   change can remove this physical loss.
2. **Cold WANOPT flows pay a new QUIC handshake and control exchange.** The
   outer handshake is the dominant cold-start cost; pooling removes most of
   that fixed cost, while `OPEN_FAST` makes the server-side open work
   negligible.
3. **The current `bbr-tuic` sender overreacts to this loss window.** Its
   delivery estimator and recovery logic drive the US-side congestion window
   down to tens of KiB, so a single logical flow is much slower than TUIC and
   even slower than the BBR-shaped experiment. This is the main WANOPT-specific
   bulk bottleneck in this profile.

The evidence does **not** support CPU, HMAC authentication, US-side DNS, or
destination TCP connect as explanations for the seconds-long latency. It also
does not justify selecting `bbr-tuic`, four lanes, or a fixed-rate controller
globally: those choices trade loss resilience, queueing, and lane churn against
goodput and must be gated by live path-health telemetry.

## Immediate engineering implications

- Keep a persistent, low-rate control/pool path for one-shot and interactive
  requests; do not create a fresh QUIC connection for every request.
- Treat `bbr-tuic` as experimental until its loss/recovery behavior is fixed
  or it can prove parity with TUIC over repeated matched campaigns.
- Use the controller's directional loss, delivery estimate, cwnd, RTT, and
  recovery state for admission and demotion decisions. The generic QUIC loss
  counters alone are insufficient with an externally installed controller.
- Permit additional lanes only after a measured bulk promotion threshold and
  cap them with a health/RTT budget. Four lanes can rescue throughput in this
  window, but lane setup and failure churn make them unsuitable as a default.
- Keep bounded TCP fallback enabled. The measured UDP impairment is severe
  enough that a production client must race or quickly fall back to TCP for
  cold control flows when QUIC PTOs exceed the latency budget.

The next controller work should use this profile as a regression baseline:
replay the observed RTT/loss distribution, compare the TUIC-aligned estimator
against BBR-shaped, TUIC, and the stock Reno controller, and require matched
single-flow, interactive-under-bulk, upload, and failure-recovery gates before
changing the production default.

## Refreshed profile with optimistic open

The following isolated campaign used the current worktree (including the
opt-in `--optimistic-open` implementation), a temporary WANOPT listener on
`23.135.236.244:12451`, and a US-side zero-filled HTTP oracle on `:28084`.
The production WANOPT listener, local WANOPT SOCKS node, and local TUIC node
were not changed. The client forced QUIC so that TCP fallback did not obscure
the stage timings.

### Warm request control

Two persistent pooled clients were warmed and then exercised in an interleaved
sequence of 15 one-KiB requests each. Both endpoints returned HTTP 200 and the
exact 1,024-byte body on every trial:

| Profile | Median | p95 (nearest rank) | Maximum | Completion |
|---|---:|---:|---:|---:|
| WANOPT pooled, optimistic open | 0.184 s | 0.771 s | 0.771 s | 15/15 |
| WANOPT pooled, normal `OPEN_OK` | 0.359 s | 0.963 s | 0.993 s | 15/15 |
| TUIC persistent control (same oracle, separate sample) | 0.238 s | 0.246 s | 0.246 s | 10/10 |

The local debug trace measured `OPEN_FAST` stream-open durations below
0.12 ms with optimistic mode. With the normal mode, the same operation took
approximately 0.17--0.18 s. The remote server recorded zero-millisecond
`OPEN_FAST` processing and 0.3--0.6 ms destination dials. Consequently, the
approximately 175-ms median difference is a protocol acknowledgement RTT,
not server work. Optimistic open overlaps this acknowledgement with the SOCKS
application exchange; a later `RESET` remains an application-visible failure.

The first request on a newly created pool still took 0.73--0.94 s in this
window. This is the outer QUIC/TLS handshake and cannot be removed by stream
optimism. A fresh, non-pooled client produced five exact one-KiB requests in
0.971, 1.459, 1.489, 1.540, and 1.688 s (median 1.489 s); its local traces
showed outer dial times from 0.204 to 1.137 s. The remote authentication and
destination dial remained below 0.7 ms.

For context, direct TCP HTTP to the same public oracle took 0.998--1.081 s
(median 1.028 s) and ten ICMP probes to the fixed egress had 30% loss with
178.8-ms mean RTT. The ICMP result is only a path-health indicator, but it
explains why the QUIC handshake has a long and variable tail. TUIC's persistent
connection avoids that repeated handshake and was correspondingly steadier in
the separate 10-request sample.

### Bulk and interactive traffic on the current controller

One pooled `bbr-tuic` client downloaded the exact 10-MiB oracle object while
20 serial one-KiB requests were issued through the same local endpoint. The
bulk request timed out at the 60-s bound after 3,375,104 bytes (56.2 KiB/s).
During the transfer, one-second remote metrics samples showed:

- smoothed RTT of 175--181 ms;
- maximum delivery estimates oscillating between approximately 20 and 74
  KiB/s;
- pacing pinned to the configured 64-KiB/s floor;
- congestion window repeatedly falling to 4.8--12 KiB (occasionally rising to
  25--35 KiB); and
- 1.19 MiB and 1,007 packets reported lost before the lane failed near the
  end of the sample.

The interactive requests all completed, but their total times were
0.202--1.180 s (median approximately 0.484 s, p95 approximately 0.814 s).
Their `OPEN_FAST` operations remained sub-millisecond; the tail came from
loss/recovery and queueing on the shared QUIC path while the bulk controller
was in recovery. This is the dominant reason the approach can still feel
slow even after pooled stream setup has been optimized.

### Updated diagnosis

The measurements separate the remaining latency into three independent
budgets:

1. **Path budget:** the China-to-US path currently loses roughly 30% of ICMP
   probes and has about 179 ms RTT. QUIC PTO/retransmission gaps dominate
   cold-start tails.
2. **Protocol budget:** a new outer QUIC connection costs roughly 0.2--1.1 s
   in this window; a pooled normal flow adds about one RTT for `OPEN_OK`.
   Optimistic open removes the latter but cannot repair a lost outer path.
3. **Controller budget:** `bbr-tuic` reacts to the observed loss by reducing
   delivery estimates, pacing, and cwnd to the floor. It therefore causes
   both the 56-KiB/s single-flow bulk result and sub-second interactive tails.

The evidence does not implicate Go CPU, HMAC authentication, remote DNS, or
the US-side destination TCP connect. The next performance change should be a
controlled sender/recovery experiment (with loss and cwnd guardrails), not
more stream-open pipelining or additional fixed lanes.

## Fresh controller attribution run

To check that conclusion against the newest uncommitted TUIC-startup fixes, I
ran a second isolated campaign on 2026-08-11. The production `:12443` service,
the local WANOPT `:12081` node, and the local TUIC `:12086` node were not
changed. The new WANOPT listener was `:12457` with metrics on `:19099`; a
matched stock BBR-shaped control used `:12458`/`:19100`. Both used the same
temporary US HTTP oracle on `:28086`, the same secret and certificate, one
pooled QUIC lane, `--optimistic-open`, and an exact 1-MiB body.

The path was slightly healthier but still materially impaired during this
run: 20 ICMP probes produced 15 replies (25% loss), with
`177.878/179.982/187.163 ms` min/mean/max RTT. Direct TCP HTTP to the oracle
took `1.014--1.112 s` for 1 KiB.

### Latency and single-flow bulk

The first WANOPT request on a new pool took `5.691 s`. The client trace
attributes `5.507 s` to the outer QUIC dial; authentication took 1.8 us and
the pooled stream was then ready. On the remote side, the same first flow had
authentication `0.216 ms`, destination dialing `0.593 ms`, and an
`open_duration` of `3.659 s`, which is a lost/delayed control exchange rather
than server work. Later pooled one-KiB requests completed in
`0.182--0.726 s` (most were `0.182--0.386 s`); `OPEN_FAST` itself remained
below 0.12 ms. Ten-request medians were approximately `0.235 s` for TUIC,
`0.273 s` for WANOPT bbr-tuic, and `0.180 s` for stock BBR-shaped, with
occasional 0.6--0.7-s tails on both WANOPT profiles. The bbr-tuic median is
pulled up by several 0.36--0.73-s samples even though its best samples are
close to one RTT.

Repeated exact 1-MiB single-flow downloads were:

| Profile | Trial times | Goodput range |
|---|---|---:|
| TUIC persistent | 1.238, 1.157, 1.156 s | 0.83--0.91 MiB/s |
| WANOPT `bbr-tuic` | 21.69, 27.84, 20.75, 22.11 s | 36.6--50.5 KiB/s |
| WANOPT stock BBR-shaped | 6.71, 2.70, 2.27 s | 156--463 KiB/s |

Thus stream framing and destination access are not sufficient explanations:
the same WANOPT framing with the stock controller is 3--10 times faster than
`bbr-tuic`, while native TUIC is another 2--5 times faster on this window.

### Remote controller telemetry during a 22.11-s `bbr-tuic` transfer

The US sender reported a stable `0.178--0.180 s` minimum/smoothed RTT, but:

- maximum delivery estimates oscillated from `19.7` to `66.0 KiB/s`;
- pacing stayed at or near the `64-KiB/s` safety floor;
- cwnd oscillated between `4.8` and `32 KiB` and was repeatedly capped by
  recovery; and
- the custom controller accumulated about `3.56 MiB`/`3,046` lost bytes and
  packets by the end of the transfer, while it remained in recovery for most
  samples.

The stock QUIC `ConnectionStats` loss fields are not authoritative for an
externally installed controller: quic-go updates those fields inside its
stock loss callback, while the custom controller owns the extended callback.
The controller's directional loss counters, cwnd, pacing, and delivery
estimate are therefore the relevant diagnosis. The loss/recovery loop is
driving the sender to a tens-of-KiB operating point; no amount of
authentication or US-side optimization can compensate for that.

### Current conclusion

There are two different “high latency” symptoms:

1. A cold flow can take several seconds because the lossy UDP path delays the
   outer QUIC handshake and, in one trace, the pipelined `OPEN` frame. Pooling
   and optimistic open remove most avoidable control RTTs, but cannot remove
   PTOs on a 180-ms path with 25% loss.
2. A warm bulk flow can make interactive requests feel slow because the
   `bbr-tuic` sender enters persistent loss recovery, shrinks cwnd, and paces
   at its floor. This is a WANOPT-specific controller failure, not a physical
   latency lower bound.

Until the recovery/sampler behavior is corrected and passes repeated matched
loss campaigns, `bbr-tuic` should remain opt-in. The stock BBR-shaped
controller is the faster experimental WANOPT control in this measurement,
but it is not yet a production recommendation either; the release default
should continue to use the validated Reno/AUTO fallback path.

## Sampler-instrumented latency refresh

I repeated the profile on 2026-08-11 after adding loopback-only sampler
diagnostics. The diagnostics expose the latest raw ACK and send-rate samples,
sample counts, app-limited counts, packet-state misses, zero-rate samples, and
the BBR round. The isolated resources were WANOPT `:12459`, local pooled
SOCKS `:12164`, local non-pooled SOCKS `:12165`, metrics `:19101`, `:19164`,
and `:19165`, plus the US oracle on `:28087`. Production `:12443`, local
WANOPT `:12081`, and TUIC `:12086` were not modified.

The path was healthier than the earlier campaign but still lossy: 20 ICMP
probes had 18 replies (10% loss), with `172.8/180.1/183.7 ms`
min/mean/max RTT. This is an important control variable: the same code can
have a one-RTT result when the path is clean and a multi-RTT tail when a
control or data packet crosses a loss/PTO boundary.

### Cold and warm one-shot requests

Ten independent, non-pooled 1-KiB requests all completed successfully. Total
times were:

```text
0.545, 1.262, 0.910, 0.546, 1.250,
0.743, 0.741, 1.769, 0.910, 0.550 s
```

The median was `0.826 s`, p90 `1.262 s`, and maximum `1.769 s`. Client logs
split the delay into the outer QUIC dial and the application exchange. Outer
dials were `0.187--1.422 s` (median approximately `0.383 s`); authentication
was `10--39 us`. The local `OPEN`/flow-open duration was one additional
approximately `0.18 s` RTT after a successful dial. Remote authentication and
destination TCP dials remained below `0.7 ms`. Therefore the cold tail is
transport loss/PTO, not HMAC, TLS certificate work, DNS, or US destination
setup.

After the pool was warm, ten serial 1-KiB requests through the same pooled
lane were `0.196--0.199 s` each in a clean interval. That is essentially one
China-US RTT. This is evidence that WANOPT does not have an intrinsic
one-second latency floor; the seconds-long values are cold-start loss and
queue/recovery tails.

### Interactive traffic during bulk

One 10-MiB download was run on the pooled lane while 20 serial 1-KiB requests
were issued on additional streams. The request first-byte times were
`0.210--0.524 s`; total times were `0.246--0.748 s` (median approximately
`0.279 s`, p95 `0.590 s`, maximum `0.748 s`). All 20 returned HTTP 200 and
exactly 1,024 bytes. In the same interval a separate TUIC control endpoint,
not sharing the WANOPT bulk connection, remained at `0.234--0.238 s`; that is
only a path control and not a same-connection fairness comparison.

The US-side controller snapshot during the bulk run showed approximately:

```text
smoothed RTT                 0.194 s
latest ACK sample            55--63 KiB/s
latest send sample           9--12 KiB/s
max delivery estimate        30--67 KiB/s
pacing                       64 KiB/s floor
cwnd                         12--34 KiB
recovery                     true
directional loss             739 KiB / 648 packets (at 5.26 MiB sent)
```

The client-side sampler, which mostly sees the tiny request/ACK direction,
produced intentionally tiny samples (roughly `95--343 B/s`) and is not the
download bottleneck. It did, however, reveal that 175 of 454 samples during
the long run were app-limited because short request streams intermittently
drained the shared connection. The server sender had 3,943 non-app-limited
samples and only 32 app-limited samples, so its low estimate is not explained
by a sampler state miss (`1` state miss) or by treating the bulk sender as
idle. It is a genuine send-rate/recovery collapse under observed loss.

The bulk body did not pass the 180-s completion gate: curl received
9,207,808 of 10,485,760 bytes (`51.2 KiB/s`) before timeout. The local flow
then attempted four bounded replacement lanes after the application had
already timed out; this generated five lane-failure and four replacement
counters before cleanup. That is a separate lifecycle inefficiency to fix,
not a reason to attribute the request's first-byte latency to the US
destination.

### Attribution

The refreshed evidence separates four effects:

1. **Physical path:** approximately 180-ms RTT with 10% observed ICMP loss;
   retransmission/PTO events add whole RTTs to the tail.
2. **Cold control plane:** a fresh QUIC dial can consume 0.18--1.42 s, then
   the first stream/open exchange adds about 0.18 s. A persistent pool and
   optimistic open remove these avoidable exchanges.
3. **Shared-connection queueing:** while bulk is active, interactive streams
   still start in about one RTT but their body completion grows to
   0.25--0.75 s because the current pool has no strict interactive scheduling
   or independent control lane.
4. **`bbr-tuic` bulk recovery:** the US sender's low delivery estimate, floor
   pacing, small recovery-capped cwnd, and directional loss limit both bulk
   throughput and the tail of multiplexed interactive streams. CPU and
   destination dialing are not implicated.

The next performance change should therefore target admission/scheduling and
controller recovery separately: keep a reserved interactive/control lane (or
strict stream priority) during bulk, and do not enable `bbr-tuic` until its
single-flow rate model is at least competitive with native TUIC under a
matched loss/reordering campaign.

## Send-baseline correction and matched rerun

I repeated the isolated campaign after auditing the packet sampler against
sing-quic's `congestion_meta2` implementation. Production `:12443`, local
WANOPT `:12081`, and TUIC `:12086` were not changed. The temporary resources
were WANOPT QUIC `:12462`, server metrics `127.0.0.1:19162`, local pooled SOCKS
`:12162`, local non-pooled SOCKS `:12164`, and the bounded US oracle on
`:28088`.

The audit found that each packet correctly retained its send-time ACK point,
but the send-rate calculation used the sampler's later *global* ACK point.
When ACKs were interleaved, this subtracted bytes that were not part of the
packet's original S0 baseline. The resulting send slope was often an order of
magnitude too small, and the `min(send_rate, ack_rate)` sample drove pacing to
the 64-KiB/s safety floor. A deterministic interleaving test now guards this
case.

The matched 1-MiB results show the effect:

| Profile | Trials (seconds) | Median | Goodput range |
|---|---:|---:|---:|
| Old isolated `bbr-tuic` sampler | 19.27, 18.80, 18.69, 18.89 | 18.85 | 54–56 KiB/s |
| Corrected `bbr-tuic`, fresh pooled connection | 3.80, 2.52, 2.51, 2.29 | 2.52 | 276–459 KiB/s |
| Native TUIC, same oracle/window | 1.51, 1.16, 1.25 | 1.25 | 692–905 KiB/s |

The first corrected run's server telemetry reached a delivery estimate of
`1,005,733 B/s` (latest sample `1,002,037 B/s`, send slope `1,191,617 B/s`),
with a 365-KiB congestion window and one reported 1,145-byte loss. This is
direct evidence that the estimator can now observe the path capacity rather
than being pinned by a bad baseline. Later runs on the same long-lived pool
fell to roughly 160–245 KiB/s estimates after a loss/recovery episode; the
controller remains conservative when its ten-round max filter expires and it
has to probe again. That tail still requires a matched TUIC parity campaign.

### Latency stages

Eight fresh, non-pooled 1-KiB flows through corrected `bbr-tuic` took:

```text
0.785, 0.528, 2.383, 0.537, 1.125, 0.910, 1.990, 1.195 s
```

The median was `1.02 s`; the maximum was `2.38 s`. Client debug timing split
the successful exchanges into:

- outer QUIC dial: approximately `0.18–1.51 s`;
- HMAC/session authentication: tens of microseconds; and
- non-optimistic stream open: approximately one additional `0.18–0.67 s`.

The remote server measured authentication in roughly `0.01–0.23 ms` and
destination TCP dialing in `0.29–0.88 ms`. Thus the cold tail is still the
lossy QUIC handshake/PTO path plus the intentionally sequential OPEN
acknowledgement, not TLS, HMAC, DNS, or US-side destination work.

Once the pool was established and optimistic OPEN was enabled, ten serial
1-KiB requests were `0.184–0.187 s` (all complete). This is one physical
China–US RTT and confirms that the protocol does not impose a one-second
latency floor. During a 1-MiB transfer, ten additional requests completed in
`0.226–0.908 s` (median approximately `0.32 s`); this is shared-connection
queueing and loss recovery, not remote application latency.

```text
20 ICMP probes: 17 replies (15% loss)

```

Direct HTTP to the same US-side oracle took `0.940–1.148 s` for a 1-KiB

connection handshake, `flow open` is measured from SOCKS handling start until

the internal logical-flow cleanup time after the body has normally already
been delivered.

| Profile | Application result | Outer dial | Flow-open stage | Interpretation |
|---|---:|---:|---:|---|
| Pooled + optimistic OPEN, warm | 10/10; `0.174–0.679 s`, median `0.177 s` | `0.014–0.060 ms` for later streams | first stream `0.359 s`; later `OPEN_FAST` below `0.2 ms` locally | Healthy requests are approximately one RTT; the `0.679 s` tail is a transport loss/PTO event |
| Pooled, normal OPEN | 6/6; `0.360–1.503 s`, median `0.363 s` | first pool `0.936 s`; later streams below `0.05 ms` | later streams about `0.179 s` | Waiting for `OPEN_OK` adds one China–US RTT to every warm request |

The remote server's authentication and destination TCP dial remained in the

A five-second macOS `sample` during a 100-MiB transfer showed the client

The local `flow complete` log often remains open for `0.35–0.50 s` after a

intentional `remoteFinDrainGrace = 500 ms` close-race protection in

It affects cleanup latency and lane availability, not the HTTP response's
first-byte or body-completion time. Reducing it is a separate correctness
experiment and should not be used to explain the observed cold request tails.

### Updated diagnosis

The current profile confirms the earlier causal split:

1. **Warm request latency:** pooled optimistic streams are approximately one
   physical RTT. WANOPT is not intrinsically a one-second protocol.
2. **Cold request latency:** a new QUIC handshake plus the first HelloOK costs
   roughly `0.2–1.1 s`, and path loss can add another PTO. Pool prewarming,
   connection resumption/0-RTT, and fast stream open are the relevant fixes.
3. **Normal pooled stream latency:** waiting for `OPEN_OK` adds one RTT even
   though server authentication and destination dialing are negligible.
4. **Bulk/interactive tails:** when loss causes `bbr-tuic` to enter persistent
   recovery, its delivery estimate, pacing, and cwnd can collapse as shown in
   the earlier campaigns. The clean-run parity above is not evidence that the
   loss behavior is fixed.
5. **Resource overhead:** CPU, HMAC, TLS, and destination setup are not
   responsible for seconds-long latency. The flow-close grace is visible in
   internal teardown logs but is not application-visible response latency.

The safe conclusion is still to keep `bbr-tuic` opt-in, keep one pooled
control/interactive path warm, and gate bulk lane promotion and controller
changes on repeated loss-window campaigns rather than on this clean interval.

The correction is therefore material but not a release qualification: it
removes a sampler bug and restores multi-hundred-KiB/s to approximately
1-MiB/s estimates, yet native TUIC is still about 2× faster in the cleanest
matched samples and has a better tail. `bbr-tuic` remains opt-in until it
passes repeated fresh/warm, upload, interactive-under-bulk, and loss/fallback
gates against native TUIC.

application latency. The safe latency configuration remains a pre-warmed
pooled control path with optimistic/fast stream open, bounded TCP fallback,
and a separate, measured bulk lane; the production default should not change
until the controller and priority scheduler pass the full regression matrix.

### Why the local priority queue cannot solve this by itself

The recent writer change reserves eight of 64 PEP queue slots for interactive
frames and drains that queue first. That prevents a bulk producer from filling
one *PEP lane's* user-space queue, but it does not control the pooled QUIC
connection. The apNet QUIC fork's `framer.getNextStreamFrame` uses a ring
buffer: it pops an active stream, emits one STREAM frame, and appends the
stream at the back when more data remains. There is no public stream-priority
API. Consequently, all PEP streams still share one congestion window and one
loss-recovery state; a lost/retransmitted bulk packet can consume the same
recovery budget as an interactive packet. The measured p95/max behavior is
consistent with that design.

### Profile conclusion

The current high-latency symptom is a sum of three effects, with different
remedies:

1. A lossy 178-ms physical path adds PTO-sized tails that no proxy framing can
   eliminate.
2. A fresh flow pays a new QUIC handshake; pooling and optimistic open remove
   healthy control RTTs but cannot repair a lost Initial/Handshake packet.
3. A pooled bulk flow shares QUIC congestion control with interactive streams.
   WANOPT's current controller/recovery behavior produces a much wider tail
   than native TUIC even when its median is one RTT.

The next engineering experiment should therefore be a strict control/bulk
lane split (or a QUIC fork with explicit stream priority) combined with a
repeated controller parity campaign. More authentication, destination-side
optimization, or Go CPU tuning will not address the measured bottleneck.

## Negotiated control/bulk lane experiment

The follow-up experiment implemented the strict split as a negotiated wire
capability. A capable pooled server advertises control-lane reservation; the
client opts in on the flow OPEN; and, once an independent joined lane is
healthy, bulk DATA excludes pooled lane zero. Control frames and short flows
continue to use the persistent pool. Older clients and servers retain the old
behavior because neither side sends the new flag without capability
negotiation. All listeners remained isolated (`:12520` through `:12527`);
production `:12443`, local production `:12081`, and TUIC `:12086` were not
changed.

### First isolation result and lane-churn diagnosis

Moving the classifier boundary from 256 KiB/2 s to 128 KiB/1 s made the first
independent lane appear earlier, but the initial V2/V3 scheduler was not safe.
After an RTT or negative-gain decision retired a lane, the next bulk-start
decision immediately created another. One interrupted/slow flow authenticated
lane IDs 1 through 23. More importantly, a retired lane could still contain
unacknowledged DATA. The peer correctly treated the close as failure and
replayed its outstanding window on lane zero.

That replay amplification is visible in a matched 10-MiB V3 run:

```text
WANOPT V3 application body      10,485,760 bytes in 32.052 s
server lane 0 DATA writes       13,140,174 bytes
server joined-lane DATA writes   2,162,688 bytes
native TUIC application body    10,485,760 bytes in 10.418 s
```

The lane manager was therefore a direct cause of the 32-s result. Closing a
lane is not a valid policy demotion until the protocol has an acknowledged
lane-drain operation. The corrected implementation retains every healthy
lane through flow completion, suppresses further growth after a negative
decision, exponentially backs off failed probes, and caps speculative probe
attempts. A worker error also cancels its sibling before flow teardown so the
manager cannot outlive a failed logical flow.

### Corrected V4 result

With unsafe retirement removed, three exact V4 10-MiB trials completed in
`15.001`, `15.377`, and `12.994 s` (median `15.001 s`). The independent lane
carried `6.99`, `6.65`, and `5.96 MiB`, respectively, with no policy-induced
replay cycle. Three native-TUIC controls in the immediately following window
completed in `10.492`, `10.902`, and `10.680 s` (median `10.680 s`). Thus the
split removed the severe regression but did not meet the TUIC parity gate:
the WANOPT median remained about 40% slower.

A one-lane stock BBR-shaped control was also slower in this window:
`20.105`, `15.833`, and `18.633 s`. Selecting the more aggressive-shaped
controller globally is therefore not supported by this campaign.

During a separate exact V4 10-MiB profile (`14.796 s`), one-second aggregate
telemetry across the two QUIC lanes showed:

```text
smoothed RTT                  200--271 ms
maximum delivery estimate    0.75--2.06 MB/s
pacing                        0.75--4.55 MB/s
congestion window             170--776 KiB
controller-reported loss      8.79--13.06 MiB
recovery                      true initially, then false
```

This is no longer a tens-of-KiB congestion-window collapse, but it is still a
loss-heavy controller/path regime. Server authentication and destination dial
remained sub-millisecond, and the pooled `OPEN_FAST` path on the client stayed
below 0.12 ms.

### Interactive traffic after the split

While V4 downloaded 10 MiB in `15.992 s`, 15 serial exact 1-KiB requests on
the pooled control connection completed in `0.203--0.863 s` (median
`0.405 s`, nearest-rank p95 `0.863 s`). The comparable native-TUIC sample

its bulk object completed in `10.418 s`.

The split therefore protects the pooled lane from *new* bulk writes after the
join, but it cannot instantly remove bulk packets already queued on lane zero.
The first adaptive decision was also delayed because non-bulk scheduler ticks
consumed the two-second decision interval. V5 corrects that bookkeeping: the
first bulk decision now occurs on the first tick after classification rather
than up to two seconds later.

Three V5 10-MiB trials completed in `16.461`, `14.476`, and `18.191 s`. The
joined lane carried `7.09`, `4.16`, and `7.06 MiB`. Although promotion occurred
earlier, independent QUIC setup remained path-dependent: the three lane
handshakes took approximately `1.14`, `6.45`, and `1.27 s`. The 6.45-s cold
join explains why one trial left substantially more of the object on the
control lane. It also explains why classifier tuning alone cannot close the
TUIC gap.

At the end of the campaign, 20 direct ICMP probes produced 13 replies (35%
loss) with `178.541/183.056/203.295 ms` min/mean/max RTT. ICMP is only a path
health indicator, but the repeated multi-second independent QUIC handshakes
are consistent with loss/PTO on that path.

### Updated release decision

The negotiated control reservation, bounded probes, and no-retirement rule
are correctness improvements, and all current unit/race/static checks pass.
They are not sufficient for release. The remaining bulk and interactive
parity gap is now dominated by two measurable items:

1. a bulk lane still pays a fresh, lossy QUIC handshake after classification;
   and
2. WANOPT's `bbr-tuic` integration still differs materially from native TUIC
   under the observed loss/recovery workload.

The next experiment should pre-authenticate a bounded secondary QUIC
connection and add an authenticated fast lane-join operation, so promotion
opens only a stream rather than a new connection. That feature must remain
capability-gated and opt-in until memory, idle-connection, replay, restart, UDP
block, and downgrade tests pass. Production defaults must remain unchanged
until repeated randomized campaigns show both TUIC bulk parity and tighter
interactive tails.

## Bounded early lane prewarm (V6)

To reduce the cold-join contribution without introducing a new wire type, V6
starts the existing authenticated lane join once a flow has sustained at least
64 KiB for 500 ms and is strongly asymmetric (at least 8:1 in either
direction). NEW and interactive DATA still selects lane zero; the joined lane
is only eligible after normal BULK classification. Balanced bidirectional
traffic therefore does not trigger the probe.

On the same temporary oracle, V6 exact 10-MiB trials were `14.528`, `15.120`,
and `25.643 s` (median `15.120 s`). The joined lane carried `7.50`, `7.24`,
and `7.29 MiB`. The first two trials began their independent handshake about
`1.78` and `1.57 s` after flow start, compared with roughly `2.6--6.5 s` in
the later-bound V5 samples. The third trial still took `25.6 s` because the
independent path/controller entered a much slower recovery regime; earlier
lane setup did not remove that variance.

Three warm exact 1-MiB trials completed in `2.694`, `2.760`, and `3.047 s`.
The prewarm lane carried zero bytes in the visible 1-MiB completions when its
handshake finished after the object, so this path did not turn a short request
into a second bulk stream. It does, however, consume a speculative QUIC
handshake for a one-way 1-MiB flow. The threshold and asymmetry guard are
therefore deliberately conservative and remain experimental.

V6 does not claim parity. Its evidence supports a bounded prewarm as a useful
incremental mitigation, while the remaining production-grade solution is a
capability-gated secondary QUIC pool with an authenticated fast lane-join
stream. That design would amortize the handshake without probing every
medium-sized flow, but it requires explicit server-side admission, idle-memory
limits, restart/downgrade behavior, and UDP-block fallback tests before use.
